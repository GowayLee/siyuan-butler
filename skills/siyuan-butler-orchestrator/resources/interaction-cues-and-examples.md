# Orchestrator 交互信号与例子

## 1. 继续整理，不记录

用户输入：

> 我还没想清楚，只是觉得这个方向有点怪。

处理倾向：

- 先帮用户把“怪”的地方理顺
- 不急着问保存日期或写入位置
- 不默认进入记录链路

## 2. 进入 Capture

用户输入：

> 先帮我记一下：德彪西这里不是在描写景物，而是在把景物召唤出来。

处理倾向：

- 判断为值得接住的 Sparkle
- 更偏 `affective` 或 `mixed`
- 优先保住 `source` 与 `glow`
- 在内部先完成日志目标定位与结构检查，不把这些准备动作拆成多轮追问

## 3. 进入 Rekindle

用户输入：

> 上次那条关于 declarative system 的 sparkle，我想把它写成今天的正式记录。

处理倾向：

- 明确这是一条既有 Sparkle
- 进入 rekindle，而不是重新 capture
- 需要围绕目标 Sparkle 看成熟度和落点

## 4. 停在提案层，不写入

用户输入：

> 你先帮我收一下，不一定现在写进去。

处理倾向：

- 可以形成 `SparkleDraft` 或 `RekindleProposal`
- 但不默认继续到执行链路

## 5. 进入确认边界

用户输入：

> 可以，就按这个正式写进去。

处理倾向：

- 如果上一步已经得到 `ReviewResult.ask_confirm`
- 这时才把明确确认传给执行端
- 不扩大写入范围，只执行已审查的计划

## 6. 不该外显的中间步骤

处理倾向：

- 定位日志页
- 检查 `sparkles` 段落或正文落点是否存在
- 读取最小必要上下文

这些动作默认属于 Butler 的内部准备，不应反复问用户“下一步要不要继续做这个”。
